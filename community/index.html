Engineering decisions and trade-offs

Selected examples explain why a particular implementation boundary was chosen. These are technical rationales grounded in the linked PR descriptions, not claims about personal motivation.

REA #2214 · Data contracts

Make coverage a typed fact, not a diagnostic string

Problem: complete identical inventories were incorrectly reported as unknown. Decision: declare traversal scope and completeness at the producer, then compare structured coverage independently of notice text. Why: display messages can change without changing evidence semantics; consumer-side string heuristics are fragile. Trade-off: a slightly richer evidence contract in exchange for deterministic comparisons and fewer false unknowns. Evidence: PR #2214.

REA #1533 · Build versus reuse

Use WABT rather than invent a WASM parser

Problem: saved WASM artifacts could not be inspected without an active target. Decision: admit an explicitly selected local artifact and pinned WABT tools behind a narrow adapter; preserve digests and CLI/MCP parity. Why: reuse a maintained decoder while constraining the trust boundary and provenance. Trade-off: a caller-supplied external toolchain instead of a new in-process parser. Evidence: PR #1533.

REA #2464 · Semantic comparison

Compare typed interfaces, not byte-level differences

Problem: changes in binary hashes or WAT type indices do not necessarily imply changed imports or exports. Decision: resolve typed interface facts once in the producer and compare retained Evidence without reparsing display text. Why: the comparison should answer API compatibility questions rather than file-identity questions. Trade-off: duplicate names or incomplete inventories remain unknown rather than forcing a misleading verdict. Evidence: PR #2464.

Chemprop #1379 · Dynamic shapes

Prevent export-time graph-size specialization

Problem: Python len(bmg.V) became specialized to the example molecule during torch.export, breaking inference on different graph sizes. Decision: correct message-passing allocation to respect dynamic graph dimensions rather than freezing sample-derived length. Why: an exported model must preserve the intended variable-size molecular graph contract. Trade-off: focus on the dynamic graph-size defect, with regression coverage, rather than redesigning message passing. Evidence: PR #1379.

REA #1506 · Heuristics

Prefer bounded conventions over substring inference

Problem: unrelated filenames were misclassified as Unity or Flutter, and generic Apple paths implied unsupported language/runtime conclusions. Decision: match known complete library filenames and framework path segments. Why: weak substring matches turn naming coincidences into false evidence. Trade-off: narrower detection may yield fewer hints but substantially more defensible ones, without schema changes. Evidence: PR #1506.

Sony NMOS #502 · Standards

Represent temporal redundancy explicitly

Problem: existing SDP handling did not fully express the SMPTE 2022-7 temporal redundancy form. Decision: retain SSRC-level identity, CNAME, delay and MID in structured parameters, with round-trip and invalid-input tests. Why: protocol conversions must preserve semantics and reject transport layouts that cannot be represented faithfully. Trade-off: constrain the supported topology rather than silently coercing incompatible forms. Evidence: PR #502.

OpenMed #1601 · Privacy correctness

Use context-gated deterministic identifiers

Problem: Vietnamese identifiers and contact formats were missing from offline PII recognition. Decision: add locale-specific patterns and require context for CCCD/CMND candidates that lack a public checksum. Why: treating every matching digit sequence as a national ID creates avoidable false positives. Trade-off: context gating can miss isolated identifiers; synthetic golden cases make this limitation testable. Evidence: PR #1601.

Diagram Design #101 · Visual correctness

Specify a quantitative visual contract

Problem: adding a polar example alone would not guarantee faithful quantitative encoding. Decision: define angle/radius semantics, zero baseline, accessible variants and adversarial geometry checks. Why: visualizations should be validated against measurable semantics, not appearance alone. Trade-off: intentionally restrict the supported variants to keep verification tractable. Integrated through maintainer PR #134; original #101.

How I contribute

My focus is on making existing systems more trustworthy: preserve information at its source, validate contracts at boundaries, reduce false confidence, and add targeted regression evidence. I favor small, reviewable extensions over parallel infrastructure and avoid claiming certainty where evidence is incomplete.
