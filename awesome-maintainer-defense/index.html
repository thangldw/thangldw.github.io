WHY THIS TOOL EXISTS

Security findings need context before action.

Repository policy and workflow configuration can hide dangerous trust boundaries. Review local evidence first, then propose a change through normal ownership and CI.

HOW IT WORKS

From a real problem to a reviewable result.

01

Inspect the repository

Audit local governance files, workflow permissions, mutable Action references and trust boundaries without a token.

02

Review each finding

Inspect evidence, severity and a stable rule ID. Findings are review leads, not proof of compromise or intent.

03

Propose a reversible patch

Generate a unified diff, check it, and apply through the repository owner’s normal review and CI process.

THE PRODUCT CONTRACT

Inspect the path from input to outcome.

01

Offline audit

Read local governance and workflow files without executing repository code.

02

Traceable findings

Review severity, stable rule IDs and evidence in repository context.

03

Patch-only remediation

Generate a unified diff; the target stays unchanged until an owner applies it.

SCOPE & LIMITATIONS

Know what the evidence proves.

Does not execute repository code or inspect live GitHub settings. No field-accuracy, compliance or authorship claims. Patch generation does not modify the target repository.

Report an issue →

BEFORE YOU START

Questions worth answering.

Does it inspect live GitHub settings?

No. The auditor inspects local files without a token or network request. Live settings and representative field accuracy are outside its evidence scope.

Does fix apply changes?

No. It generates a unified diff. Review it, run git apply --check, and apply through your normal repository process.
